Visual Studio 자동화가 갑자기 실패한다면? 범인은 강제 업데이트 팝업

김포프 2026-10-29
  • 비주얼스튜디오
  • 자동화
  • C#
  • 디버깅
  • 개발

나는 업무든 일상생활이든 반복적인 작업을 자동화하는 것을 좋아한다. 처음 자동화를 만드는 데 시간이 좀 걸리더라도 일단 만들어 놓으면 이후에는 거의 신경 쓸 필요가 없기 때문이다. 물론 자동화가 잘 돌아간다는 전제하에서 말이다.

여기서 말하는 자동화는 요즘 유행하는 AI 기반 자동화와는 조금 다르다. AI를 이용한 자동화는 기본적으로 비결정적(Non-deterministic)이다. 같은 입력을 주더라도 매번 같은 결과가 나온다는 보장이 없다. 반면 내가 주로 사용하는 것은 정해진 절차에 따라 동작하는 결정적(Deterministic) 자동화다. 동일한 환경과 입력이라면 항상 동일한 결과가 나오는 것을 목표로 한다.

그런데 최근에 오랫동안 잘 돌아가던 자동화 하나가 갑자기 실패하기 시작했다. 원인을 찾아보니 코드의 문제가 아니라 Visual Studio의 강제 업데이트 팝업 때문이었다.

Visual Studio IDE까지 자동화한다

내 자동화 스택 중에서 조금 특이한 부분이 있다면 Visual Studio IDE 자체를 직접 제어하는 자동화가 있다는 것이다.

단순히 명령줄에서 dotnet build나 MSBuild를 실행하는 것이 아니다. Visual Studio를 실행하고, 솔루션을 열고, IDE가 제공하는 여러 기능을 외부 프로그램에서 직접 조작한다.

이런 작업은 C#에서 EnvDTE, EnvDTE80 등의 라이브러리를 이용해 구현할 수 있다. Visual Studio가 제공하는 COM 기반 자동화 인터페이스다.

문제는 이쪽 API가 그다지 친절하지 않다는 것이다. 문서화도 충분하지 않은 편이고, 실제로 사용해 보면 예상과 다르게 동작하는 부분도 있다. 결국 직접 실험해 가며 삽질해야 하는 경우가 많다.

그래도 한번 제대로 만들어 놓으면 상당히 유용하다. 일반적인 명령줄 도구로는 처리하기 어려운 IDE 작업까지 자동화할 수 있기 때문이다.

갑자기 실패하기 시작한 자동화

그런데 최근에 이 자동화가 갑자기 실패하기 시작했다.

Visual Studio를 실행하고 처음 몇 개의 작업은 정상적으로 수행한다. 대략 3~4개 정도의 COM 호출이 성공한 뒤부터 갑자기 예외가 발생하는 것이다.

오류 메시지는 대략 다음과 같은 종류였던 것으로 기억한다.

System.Runtime.InteropServices.COMException (0x8001010A):
The message filter indicated that the application is busy.
(Exception from HRESULT: 0x8001010A (RPC_E_SERVERCALL_RETRYLATER))

당시 오류 메시지를 따로 기록해 두지 않아 정확히 기억나지는 않는다. 다만 프로그램이 바쁘니 나중에 다시 시도하라는 내용이었고, 아마 RPC_E_SERVERCALL_RETRYLATER 오류가 아니었을까 싶다.

사실 Visual Studio를 COM으로 자동화하다 보면 이런 오류가 아주 낯설지는 않다. Visual Studio가 다른 작업을 처리하느라 바쁘거나 일시적으로 외부 호출에 응답하지 못하는 경우가 있기 때문이다.

그래서 내 자동화에는 이미 재시도(Retry) 로직이 들어가 있다. 이런 오류가 발생하면 잠시 기다렸다가 동일한 작업을 다시 시도한다. 일반적으로는 몇 번 재시도하면 정상적으로 진행된다.

그런데 이번에는 달랐다.

아무리 재시도해도 계속 실패하는 것이다. 일시적으로 바쁜 상태라면 언젠가는 풀려야 하는데, 기다려도 상황이 달라지지 않았다. 사실상 무한 재시도 상태에 빠진 셈이다.

게다가 처음 몇 개의 작업은 정상적으로 수행한다는 점도 이상했다. 처음부터 실패한다면 설정이나 COM 인터페이스 자체에 문제가 있다고 의심할 수 있겠지만, 멀쩡하게 동작하다가 중간부터 실패하는 것이었다.

코드가 문제인 줄 알고 삽질하다

처음에는 당연히 내 자동화 코드에 문제가 생긴 줄 알았다.

Visual Studio 업데이트로 무언가 동작이 바뀐 것은 아닌지, COM 객체를 잘못 사용하고 있는 것은 아닌지, 작업 순서 때문에 문제가 발생하는 것은 아닌지 여러 가능성을 의심했다.

그래서 이리저리 코드를 수정해 봤다. 호출 순서를 바꿔 보기도 하고, 대기 시간을 조절해 보기도 했다.

하지만 아무 소용이 없었다.

계속 비슷한 지점에서 실패했다. 재시도 횟수를 늘려도 마찬가지였다.

그러다가 문득 자동화 코드만 들여다보지 말고 Visual Studio를 직접 실행해서 무슨 일이 벌어지는지 확인해 보기로 했다.

그리고 바로 원인을 발견했다.

범인은 10초 뒤에 나타나는 팝업

문제가 발생한 컴퓨터에는 Visual Studio 2026 Community가 설치되어 있었다.

Visual Studio를 직접 실행해 보니 처음에는 아무런 문제가 없었다. 정상적으로 IDE가 열리고 작업도 할 수 있었다.

그런데 대략 10초 정도 지나자 갑자기 모달 대화상자가 나타났다.

Visual Studio를 계속 사용하려면 업데이트해야 한다는 내용이었다.

문제는 이 대화상자가 단순한 알림이 아니었다는 것이다. 업데이트를 요구하는 모달 창이 떠 있는 동안에는 다른 IDE 작업을 진행할 수 없었다.

이제야 모든 증상이 설명됐다.

자동화가 Visual Studio를 실행한 직후에는 정상적으로 동작한다. 따라서 처음 3~4개의 COM 호출은 성공한다. 하지만 약 10초 뒤 업데이트 대화상자가 나타나는 순간부터 IDE가 다른 작업을 받아들이지 못한다.

외부에서 호출하는 COM 인터페이스도 마찬가지다. Visual Studio가 호출을 거부하니 예외가 발생한다.

그리고 아무리 재시도해 봐야 소용이 없다. Visual Studio가 잠깐 바쁜 것이 아니라 사용자가 직접 처리해야 하는 모달 대화상자에 막혀 있기 때문이다.

내가 자동화 코드를 아무리 고쳐 봐야 해결될 문제가 아니었던 것이다.

Visual Studio Community는 180일 이내에 업데이트해야 한다

도대체 언제부터 Visual Studio가 이렇게 강제로 업데이트를 요구하는지 궁금해서 Microsoft 공식 문서를 찾아봤다.

확인해 보니 Visual Studio 2026 Community에는 다음과 같은 정책이 명시되어 있었다.

You must update to the latest release of the Community or Team Explorer edition within 180 days to continue using the product.

즉, Visual Studio 2026 Community는 최신 릴리스가 나온 뒤 180일 이내에 업데이트해야 계속 사용할 수 있다는 것이다.

출처: Visual Studio Product Lifecycle and Servicing

Visual Studio 2026의 Community와 Team Explorer에 적용되는 정책이다. 반면 Professional과 Enterprise에는 장기 서비스 채널(LTSC) 등 보다 유연한 업데이트 및 지원 정책이 제공된다.

물론 소프트웨어를 최신 상태로 유지하는 것은 중요하다. 보안 문제도 있고 버그 수정도 필요하다. 무료로 제공되는 Community 버전에 이런 조건을 붙이는 것도 Microsoft의 정책이니 어쩔 수 없다.

하지만 무인 자동화를 돌리는 입장에서는 이야기가 조금 다르다.

내가 원하지 않는 시점에 IDE가 갑자기 업데이트를 요구하고, 그전까지 다른 작업을 진행하지 못하게 막아 버리면 자동화 전체가 중단된다.

게다가 겉으로 드러나는 오류는 업데이트 관련 메시지가 아니라 COM 호출 실패다. 원인을 모르면 엉뚱한 곳에서 한참 삽질하기 쉽다.

참고로 180일 업데이트 조건이 Visual Studio 2026에서 처음 도입된 것이라고 단정할 수는 없다. 여기서 중요한 것은 현재 Visual Studio 2026 Community에 이러한 사용 조건이 명시되어 있고, 실제로 업데이트를 요구하는 모달 창이 자동화를 방해했다는 점이다.

자동화의 의외의 적은 팝업이다

이번 문제의 원인은 결국 코드가 아니었다. COM 인터페이스 자체가 고장 난 것도 아니었고, 재시도 로직에 문제가 있었던 것도 아니었다.

그저 Visual Studio가 모달 대화상자 하나를 띄운 것이 문제였다.

사람이 직접 프로그램을 사용하고 있었다면 별일도 아니었을 것이다. 팝업을 보고 업데이트하면 그만이니까.

하지만 무인 자동화 환경에서는 이런 작은 차이가 치명적일 수 있다. 화면에 무슨 창이 떠 있는지 확인할 사람이 없고, 프로그램은 자신이 호출한 COM 메서드가 왜 실패하는지도 알지 못한다.

특히 이번처럼 처음에는 잘 동작하다가 일정 시간이 지난 후부터 실패하는 경우에는 문제를 더욱 찾기 어렵다.

이번 일을 겪으며 다시 한번 느낀 것은 자동화에서 재시도 로직만큼이나 실패를 감지하고 적절한 시점에 중단하는 로직도 중요하다는 점이다. 일시적인 오류라면 재시도로 해결되겠지만, 영구적으로 해결되지 않는 문제라면 무한히 재시도하는 것은 의미가 없다.

또한 자동화 대상 프로그램의 업데이트 정책이나 라이선스 정책도 무시할 수 없다. 프로그램의 기능이 정상적으로 동작하더라도 운영 정책 때문에 자동화가 멈출 수 있기 때문이다.

결국 이번 문제는 Visual Studio를 업데이트하면서 해결했다.

혹시 Visual Studio를 COM으로 자동화하는 도중 갑자기 호출이 실패하기 시작했다면, 특히 처음 몇 개의 작업만 성공하고 이후부터 계속 실패한다면 자동화 코드부터 고치기 전에 Visual Studio 화면에 무슨 팝업이 떠 있는지 먼저 확인해 보길 바란다.

범인은 의외로 단순한 곳에 있을 수 있다.
