Azure DevOps 빌드 에이전트의 Capabilities가 사라진다면? 범인은 Windows 압축

김포프 2026-10-19
  • 개발
  • 윈도우
  • 닷넷
  • 디버깅
  • 빌드

회사에서 여러 대의 Windows 머신을 이용해 자체 호스팅(Self-hosted) 빌드팜을 운영하고 있다. Azure DevOps의 빌드 에이전트를 설치해서 사용하는 방식인데, 올해 4월쯤부터 이상한 문제가 발생하기 시작했다.

빌드 머신을 재부팅하면 Azure DevOps 에이전트의 System Capabilities가 제대로 등록되지 않는 것이다.

Capabilities는 에이전트가 어떤 개발 도구와 환경을 갖추고 있는지 알려주는 정보다. 예를 들어 MSBuild나 Visual Studio 같은 도구의 설치 여부와 경로가 여기에 들어간다. Azure DevOps는 이 정보를 이용해 빌드 작업을 적절한 머신에 할당한다. 따라서 이 정보가 사라지면 실제 개발 도구가 멀쩡히 설치되어 있어도 빌드 작업을 할당받지 못할 수 있다.

도무지 일관성이 없는 증상

처음에는 단순히 에이전트 초기화가 꼬인 줄 알았다. 그런데 증상이 참 희한했다.

  • 어떤 머신은 재부팅하면 정상으로 돌아왔다.
  • 어떤 머신은 몇 번을 재부팅해도 해결되지 않았다.
  • 심지어 같은 머신에서도 어떤 날은 정상이고 어떤 날은 문제가 발생했다.
  • 에이전트 서비스를 재시작하는 것으로는 해결되지 않았다.

우리 빌드팜은 관리용 Administrator 계정과 실제 빌드 에이전트를 실행하는 계정이 분리되어 있다. 그래서 처음에는 계정 권한이나 초기화 순서에 따른 문제를 의심했다.

그런데 조사하던 중 더욱 이상한 현상을 발견했다.

관리자 권한으로 명령 프롬프트(cmd.exe)를 실행하기만 해도 문제가 해결되는 것이었다.

명령어를 실행하는 것도 아니다. 그냥 관리자 권한으로 명령 프롬프트를 열었을 뿐인데 이후 Capabilities가 정상적으로 등록되는 경우가 있었다.

이쯤 되니 단순한 Azure DevOps 설정 문제는 아닌 것 같았다.

Diag 로그에서 발견한 단서

Azure DevOps 에이전트는 설치 디렉터리 아래의 _diag 폴더에 진단 로그를 남긴다. Capabilities가 제대로 등록되지 않는다면 이 로그부터 확인해 보는 것이 좋다.

우리 경우에는 .NET Framework 관련 예외가 단서였다. 특히 다음과 같은 키워드를 찾아볼 만하다.

  • MarvinHash
  • ServicePointManager
  • System.Configuration.ConfigurationErrorsException

이런 오류가 보인다고 무조건 같은 문제라는 뜻은 아니다. 다만 Capabilities 수집 과정에서 관련 예외가 발생한다면 아래에서 설명할 Windows 파일 압축 상태를 확인해 볼 가치가 있다.

자세한 삽질 과정은 생략하겠다. 어쨌든 최종적으로 찾아낸 해결책은 의외의 곳에 있었다.

범인은 Windows의 WOF 압축

문제는 다음 파일이었다.

C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config\machine.config

machine.config는 .NET Framework의 전역 설정 파일이다. 그런데 이 파일이 WOF(Windows Overlay Filter) 방식으로 압축되어 있었다.

WOF는 Windows에서 파일을 압축된 상태로 저장하고, 필요할 때 압축을 풀어 읽을 수 있도록 해주는 기능이다. Windows의 Compact OS에서도 사용하며, 일반적인 NTFS 압축과는 조금 다르다. 디스크 공간을 절약하기 위해 주로 실행 파일이나 자주 변경되지 않는 파일에 사용한다.

압축 자체가 잘못된 것은 아니다. 정상적인 Windows 기능이다.

문제는 우리 환경에서 .NET Framework가 이 파일을 사용하는 과정에 뭔가 문제가 생긴 것으로 보인다는 점이다. 정확히 내부의 어느 단계에서 실패하는지, 그리고 왜 관리자 명령 프롬프트를 실행하면 증상이 달라지는지는 확인하지 못했다.

다만 해당 파일의 압축을 해제한 뒤 문제가 사라진 것은 확인했다.

확인 및 해결 방법

관리자 권한으로 명령 프롬프트(cmd.exe)를 실행한다.

먼저 32비트와 64비트 .NET Framework의 machine.config 파일을 모두 확인한다.

compact "C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config\machine.config"
compact "C:\Windows\Microsoft.NET\Framework64\v4.0.30319\Config\machine.config"

압축되어 있는 파일은 다음 명령어로 해제한다. 우리는 압축 여부에 상관없이 두 파일 모두 다음 명령어를 실행했다.

compact /U /F /EXE "C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config\machine.config"
compact /U /F /EXE "C:\Windows\Microsoft.NET\Framework64\v4.0.30319\Config\machine.config"

각 옵션의 의미는 다음과 같다.

  • /U: 압축 해제
  • /F: 파일의 압축 또는 압축 해제 작업을 강제로 수행
  • /EXE: 일반적인 NTFS 압축이 아닌 WOF 방식으로 압축된 파일을 대상으로 처리

여기서 중요한 것은 /EXE 옵션이다. 이 옵션을 지정하지 않으면 일반 NTFS 압축 파일만 압축 해제하므로, WOF로 압축된 파일은 그대로 남을 수 있다.

압축 해제가 끝나면 다시 compact 명령어로 두 파일의 상태를 확인한다. 이후 머신을 재부팅하고 Azure DevOps에서 해당 에이전트의 System Capabilities가 정상적으로 등록되는지 확인하면 된다.

우리는 이 방법으로 문제를 해결했다.

나머지 빌드 머신도 모두 처리

문제가 발생했던 머신에서 해결되는 것을 확인한 뒤, 다른 빌드 머신에도 같은 조치를 적용했다.

사실 모든 머신에서 문제가 재현된 것은 아니었다. 어떤 머신은 계속 정상적으로 동작하고 있었지만, 앞으로 같은 문제가 발생하지 않으리라는 보장도 없었다.

게다가 machine.config는 크기가 작은 설정 파일이다. 압축을 해제해 봐야 디스크 공간 차이는 무시해도 될 정도다. 굳이 압축 상태로 유지할 이유가 없다고 판단해서 모든 빌드 머신에서 32비트와 64비트 파일을 모두 압축 해제했다.

마무리

몇 달 동안 간헐적으로 발생하던 문제였는데, 결국 작은 설정 파일 하나의 압축을 해제하는 것으로 해결됐다.

물론 WOF 압축이 왜 이런 문제를 일으켰는지 정확한 내부 메커니즘은 아직 모른다. Windows나 .NET Framework의 특정 코드 경로에서 문제가 발생한 것인지, 아니면 다른 환경적 요인과 결합한 결과인지는 더 조사해야 한다.

하지만 실제로 문제가 발생하던 머신에서 압축 해제 후 정상 동작하는 것은 확인했다.

Azure DevOps의 System Capabilities가 재부팅 후 갑자기 사라진다면, 에이전트 설정을 뜯어고치기 전에 machine.config의 압축 상태부터 확인해 보자.
