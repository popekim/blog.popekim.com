윈도우 + 비주얼 스튜디오에서 .NET MAUI 업데이트 후 빌드가 깨진다면?

김포프 2026-10-20
  • dotnet
  • maui
  • nuget
  • visual studio
  • vcs
  • 개발

Windows에서 Visual Studio로 .NET MAUI 프로젝트를 개발하다 보면 NuGet 패키지 관리자에 업데이트가 잔뜩 표시되는 경우가 있다. 평소처럼 업데이트 버튼을 눌렀는데 갑자기 빌드가 깨진다면? 특히 Microsoft.Maui.Controls 같은 MAUI 관련 패키지를 업데이트한 직후라면 이 글을 읽어보자.

일반적인 NuGet 패키지와 달리 .NET MAUI는 조금 더 신경 써야 할 부분이 있다.

.NET MAUI는 NuGet 패키지만으로 돌아가지 않는다

.NET MAUI는 크게 두 가지에 의존한다.

  1. NuGet 패키지: Microsoft.Maui.Controls 등 프로젝트에서 참조하는 라이브러리
  2. .NET Workload: Android, iOS, Windows 등을 대상으로 빌드하는 데 필요한 SDK와 도구

문제는 이 둘의 업데이트가 별개라는 것이다. NuGet 패키지를 업데이트했다고 해서 해당 버전에 필요한 Workload까지 자동으로 업데이트되는 것은 아니다.

예를 들어 프로젝트에서 새로운 버전의 Microsoft.Maui.Controls를 참조하도록 변경했는데, 개발 머신에 설치된 Workload는 이전 버전이라면 호환성 문제가 발생할 수 있다. 이때는 빌드 오류가 나거나 패키지 버전이 맞지 않는다는 경고가 발생할 수 있다.

물론 NuGet 패키지와 Workload의 버전 번호가 반드시 같아야 한다는 뜻은 아니다. 중요한 것은 서로 호환되는 버전을 사용해야 한다는 것이다.

Windows + Visual Studio에서는 어떻게 해결할까?

우선 NuGet 업데이트 직후 문제가 발생했다면 해당 패키지를 이전 버전으로 롤백하자. 그러면 적어도 문제가 NuGet 업데이트와 관련 있는지 쉽게 확인할 수 있다.

그다음에는 Visual Studio Installer를 실행해서 Visual Studio와 MAUI 개발 구성 요소를 업데이트하자.

Windows에서 Visual Studio를 사용한다면 .NET MAUI Workload는 기본적으로 Visual Studio Installer를 통해 관리된다. 따라서 별도의 명령어로 Workload를 업데이트하기보다는 Visual Studio Installer를 이용하는 편이 낫다.

여기서 주의할 점이 하나 있다. 인터넷에서 MAUI 업데이트 방법을 검색하면 다음과 같은 명령어를 쉽게 찾을 수 있다.

dotnet workload update

하지만 Visual Studio Installer로 관리하는 Windows 개발 환경에서는 이 명령어를 무심코 실행하지 말자.

Visual Studio Installer로 설치한 Workload와 CLI로 설치한 Workload를 혼용하면 설치 상태나 버전 관리에 혼란이 생길 수 있다. Visual Studio가 관리하는 개발 환경이라면 업데이트도 같은 경로로 진행하는 것이 안전하다.

따라서 다음 순서로 처리하면 된다.

  1. 문제가 발생한 MAUI NuGet 패키지를 이전 버전으로 롤백한다.
  2. Visual Studio Installer에서 Visual Studio 및 MAUI 개발 구성 요소를 업데이트한다.
  3. 필요한 MAUI NuGet 패키지를 호환되는 버전으로 다시 업데이트한다.
  4. 빌드해서 정상적으로 동작하는지 확인한다.

물론 Visual Studio를 최신 버전으로 업데이트했다고 해서 모든 최신 MAUI NuGet 패키지와 호환된다는 보장은 없다. 사용 중인 .NET 버전과 Visual Studio가 지원하는 범위도 확인해야 한다.

굳이 Workload 버전까지 직접 관리해야 할까?

.NET MAUI는 global.json과 Workload Set을 이용해서 SDK 및 Workload 버전을 명시적으로 관리할 수도 있다. 특히 macOS나 CLI 중심의 개발 환경에서는 이런 방법이 필요할 수 있다.

하지만 모든 개발자가 Windows + Visual Studio를 사용하고 개발 환경까지 통일되어 있다면 이야기가 다르다.

어차피 Visual Studio Installer가 Workload를 관리하고 있는데 굳이 별도의 CLI 명령어와 버전 관리 체계를 추가할 이유가 있을까?

오히려 관리 경로가 두 개로 나뉘면서 문제가 생길 가능성만 높아질 수 있다.

결론

.NET MAUI는 단순한 NuGet 라이브러리가 아니다. 프로젝트가 참조하는 패키지뿐 아니라 개발 환경에 설치된 Workload와도 호환되어야 한다.

따라서 MAUI 관련 NuGet 패키지를 업데이트한 직후 빌드가 깨진다면 무작정 다른 패키지까지 업데이트하지 말고, 먼저 변경 사항을 롤백해서 문제를 확인하자.

그리고 Windows + Visual Studio로 개발 환경을 통일했다면 Visual Studio Installer를 통해 MAUI 개발 환경을 업데이트한 뒤 NuGet 패키지를 업데이트하면 된다.

굳이 복잡한 Workload 버전 관리 체계를 따로 만들 필요는 없다. 개발 환경을 통일했다는 것 자체가 이미 버전 관리의 상당 부분을 해결해 주기 때문이다.

버전 관리의 목적은 복잡한 설정을 유지하는 것이 아니라, 언제 어디서든 안정적으로 빌드할 수 있는 환경을 만드는 것이다.
