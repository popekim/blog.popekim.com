AI 코딩 에이전트에게 전용 개발 컴퓨터를 만들어줬다

김포프 2026-11-05
  • 인공지능
  • AI에이전트
  • 코덱스
  • Hyper V
  • 보안

예전에 포프TV를 통해 프로덕션 코드를 작성할 때는 주로 GitHub Copilot을 사용한다고 이야기한 적이 있다. 지금도 크게 다르지 않다. 내가 직접 코드를 작성하면서 AI의 도움을 받는 방식이 가장 마음에 든다.

그렇다고 AI 코딩 에이전트를 사용하지 않는 것은 아니다. 나도 필요에 따라 에이전트에게 작업을 맡긴다. 다만 에이전트가 작성한 코드를 그대로 프로덕션에 올리지는 않는다. 내게 에이전트의 결과물은 주니어 개발자가 처음 가져온 작업물 정도다. 그걸 받아서 직접 실행하고 검토한 뒤, 필요하면 수정해서 완성한다. 적어도 프로덕션에 들어가는 중요한 코드는 전부 내가 직접 검증한다는 원칙을 지키고 있다.

그런데 요즘 여러 AI 에이전트를 동시에 실행하면서 상당히 많은 작업을 맡긴다는 사람들의 이야기를 듣다 보면 가끔 당황스럽다. 생산성을 높일 수 있다는 것은 이해하지만, 그 에이전트가 실행되는 환경은 과연 안전할까?

AI 에이전트를 너무 믿는 것 아닌가?

요즘은 개인용 컴퓨터와 업무용 컴퓨터의 경계가 많이 허물어졌다. 한 컴퓨터에 개인 파일과 회사 소스 코드가 함께 있고, Git 인증 정보, SSH 키, API 토큰 등 여러 서비스의 인증 정보까지 저장되어 있는 경우가 흔하다.

게다가 많은 사람들이 Windows에 관리자 권한이 있는 계정으로 로그인해서 작업한다. 심지어 자신이 관리자 권한을 가진 계정으로 로그인하고 있다는 사실조차 모르는 경우도 있다. 물론 관리자 계정으로 로그인했다고 모든 프로그램이 항상 상승된 권한으로 실행되는 것은 아니다. 하지만 일반 사용자 계정과 비교하면 권한 상승이 훨씬 쉬운 환경인 것은 분명하다.

이런 컴퓨터에서 AI 에이전트에게 명령어 실행 권한까지 넘겨주는 것이 과연 괜찮을까?

물론 요즘 AI 코딩 에이전트들은 샌드박스(Sandbox) 기능을 제공한다. 파일 수정이나 명령어 실행, 네트워크 접근 등을 제한할 수 있다. 하지만 쓰기를 제한한다고 해서 읽기까지 제한되는 것은 아니다. 실제로 어디까지 접근할 수 있는지는 샌드박스의 구현과 설정에 따라 달라진다.

특히 각종 인증 정보가 문제다. 에이전트가 파일을 수정하지 못하더라도 민감한 정보를 읽을 수 있다면 프롬프트 인젝션(Prompt Injection) 등을 통해 정보가 유출될 가능성이 있다.

회사 컴퓨터에서만 에이전트를 실행한다고 안전한 것도 아니다. 오히려 회사 내부 시스템에 접근할 수 있는 인증 정보가 더 많이 저장되어 있을 수 있다.

나는 이런 위험을 에이전트 자체의 안전장치에만 맡기고 싶지 않았다.

AI 에이전트를 격리하는 방법

AI 에이전트의 실행 환경을 분리하는 방법은 여러 가지다.

  • 별도의 사용자 계정: 가장 간단하지만 네트워크와 일부 공유 자원까지 격리하지는 못한다.
  • Docker 등의 컨테이너: 가볍고 관리하기 편하지만 Windows GUI 개발 환경에는 제약이 있다.
  • Windows Sandbox: 간편하지만 기본적으로 일회성 환경이라 장기간 유지할 개발 환경에는 불편하다.
  • 가상 머신(VM): 별도의 운영체제와 파일 시스템을 사용하면서 네트워크까지 분리할 수 있다.
  • 별도의 물리적 컴퓨터: 독립성이 높지만 장비와 관리 비용이 추가된다.

물론 어떤 방법도 완벽한 보안을 보장하지는 않는다. 중요한 것은 내 개발 환경과 사용 목적에 맞는 방법을 선택하는 것이다.

나는 이 중에서 Hyper-V 가상 머신을 선택했다.

Hyper-V를 선택한 이유

Hyper-V를 선택한 가장 큰 이유는 성능 좋은 Windows GUI 개발 환경을 그대로 사용할 수 있다는 것이다.

나는 AI 에이전트를 터미널에서만 실행하고 싶은 것이 아니다. 필요하면 Visual Studio로 프로젝트를 열어 직접 빌드하거나 디버깅할 수도 있어야 한다. 사실상 개발 컴퓨터 한 대를 더 마련하는 것과 같은 환경을 원했다.

또 하나 중요한 이유는 실행 속도와 편의성이다.

내 메인 개발 컴퓨터는 거의 항상 켜져 있다. 별도의 물리적인 컴퓨터를 마련하면 작업할 때마다 전원을 켜거나 절전 상태에서 깨워야 한다. 반면 Hyper-V에서는 저장해 둔 VM을 재개(Resume)하기만 하면 된다. 운영체제를 처음부터 부팅할 필요도 없으니 훨씬 빠르고 간편하다.

그리고 체크포인트(Checkpoint) 기능도 마음에 들었다.

개발 환경을 처음부터 구축하려면 Windows부터 개발 도구, SDK, 각종 설정까지 손볼 것이 꽤 많다. 하지만 체크포인트를 만들어 두면 에이전트가 개발 환경을 망가뜨리더라도 정상적인 상태로 되돌릴 수 있다. 문제가 생길 때마다 처음부터 설정하는 수고를 덜 수 있다는 이야기다.

물론 체크포인트가 백업을 대체하는 것은 아니지만, 이런 용도로는 충분히 유용하다.

실제 가상 머신 구성

가상 머신에는 Windows를 설치하고 관리자 계정과 AI 에이전트 전용 일반 사용자 계정을 따로 만들었다.

관리자 계정은 개발 도구 설치나 운영체제 관리에만 사용한다. AI 에이전트는 일반 사용자 계정에서 실행하므로 운영체제 전체를 마음대로 변경하기 어렵다.

호스트와 VM 사이의 클립보드 공유 및 파일 공유 기능도 비활성화했다. 편리한 기능이기는 하지만, 호스트의 클립보드에 복사된 비밀번호나 공유 폴더의 민감한 파일에 에이전트가 접근할 경로를 굳이 열어둘 이유가 없기 때문이다.

개발 환경은 메인 컴퓨터와 거의 동일하게 구성했다. Git, SDK, 빌드 도구 등 필요한 것들을 VM에도 설치해야 하니 사실상 개발 컴퓨터 두 대를 관리하는 셈이다.

다행히 우리 회사는 모노레포(Monorepo) 구조를 사용하고 있어서 그리 어렵지는 않았다. 여러 프로젝트가 하나의 저장소와 공통된 빌드 환경을 사용하므로 기존 개발 환경을 그대로 재현하면 된다. 처음 한 번 구성하고 체크포인트를 만들어 두면 이후 관리도 비교적 간단하다.

네트워크 격리도 중요하다

VM을 사용한다고 네트워크까지 자동으로 격리되는 것은 아니다.

가상 머신에서 인터넷에 접속할 수 있다면 설정에 따라 호스트 컴퓨터나 회사 내부 네트워크에도 접근할 수 있다. 파일 시스템을 분리했더라도 네트워크를 통해 내부 서비스에 접근할 수 있다면 격리한 의미가 줄어든다.

그래서 VM에서 인트라넷으로 접근하는 것을 호스트 수준에서 제한했다.

VM 내부의 방화벽에서만 차단하면 에이전트가 설정을 변경할 가능성이 있다. 반면 호스트의 가상 네트워크와 방화벽 수준에서 제한하면 VM 안에서 동작하는 에이전트가 직접 변경하기 어렵다. 물론 실제로 차단되는 범위는 네트워크 구성에 따라 달라지므로 접근 경로를 별도로 검증해야 한다.

인터넷 연결은 유지했다. Git 저장소에 접근하고, 패키지를 다운로드하고, AI 서비스를 이용하려면 필요하기 때문이다. 다만 인터넷 접근이 가능하다는 것은 외부로 정보를 전송할 수도 있다는 뜻이므로 VM 안에 저장하는 인증 정보 역시 최소한으로 관리해야 한다.

결국 목표는 간단하다. 인터넷에는 연결되지만 내 메인 컴퓨터나 회사 내부 네트워크에는 접근할 수 없는 별도의 개발 환경을 만드는 것이다.

마무리

AI 에이전트를 사용할 때 중요한 것은 에이전트를 얼마나 신뢰하느냐보다, 문제가 발생했을 때 피해 범위를 어디까지 제한할 수 있느냐라고 생각한다.

사람에게도 업무에 필요한 권한만 부여하고 개발 환경과 프로덕션 환경을 분리한다. AI 에이전트라고 다르게 취급할 이유가 없다. 오히려 짧은 시간에 수많은 명령어를 실행하고 파일을 수정할 수 있으니 더욱 주의할 필요가 있다.

물론 모든 사람이 Hyper-V를 사용할 필요는 없다. 별도의 사용자 계정이나 Docker만으로도 충분한 경우가 있을 것이다.

하지만 나는 Windows GUI 개발 환경을 유지하면서 호스트와 격리하고 싶었다. 여기에 빠른 VM 재개와 체크포인트를 통한 복구까지 고려하니 Hyper-V가 가장 적합한 선택이었다.

AI 에이전트에게 어떤 일을 시킬지만 고민할 것이 아니라, 어떤 환경에서 어느 정도의 권한을 가지고 일하게 할 것인지도 고민해 보면 좋겠다.

나는 일단 AI 에이전트에게 개발 컴퓨터 한 대를 따로 마련해 줬다.
