I Gave My AI Coding Agent Its Own Development PC

Pope Kim Nov 5, 2026
  • ai
  • ai agent
  • codex
  • hyper v
  • security
  • dev

I mentioned on my YouTube channel, Pope TV, that I primarily use GitHub Copilot when writing production code. That hasn't changed much. I still prefer writing code myself with AI assistance.

That doesn't mean I don't use AI coding agents. I do delegate tasks to agents when appropriate. However, I don't just take their output and push it straight to production. I treat an agent's work like the first draft submitted by a junior developer. I run it, review it, and make whatever changes are necessary. My rule is that I personally verify all important code before it goes into production.

Lately, though, I've been a little surprised by people who run multiple AI agents simultaneously and give them considerable freedom to work independently. I understand the productivity benefits, but I can't help wondering: Is the environment they're running in actually safe?

Are We Trusting AI Agents Too Much?

These days, the line between personal and work computers has become increasingly blurred. It's common to have personal files, company source code, Git credentials, SSH keys, API tokens, and various other authentication details stored on the same machine.

On top of that, many Windows users do their everyday work while logged in with an account that has administrator privileges. Some don't even realize their account belongs to the Administrators group. Of course, being logged in as an administrator doesn't mean every application automatically runs with elevated privileges, thanks to User Account Control (UAC). Still, it's a very different environment from one where the user has only standard privileges.

Is it really a good idea to give an AI agent permission to execute commands on such a computer?

Modern AI coding agents do provide sandboxing features. They can restrict file modifications, command execution, and network access. But preventing an agent from writing to a file doesn't necessarily prevent it from reading that file. The actual restrictions depend on the sandbox implementation and configuration.

Authentication credentials are particularly concerning. Even if an agent cannot modify sensitive files, being able to read them could potentially lead to information leaks through prompt injection or other unintended behavior.

Running agents only on a company computer doesn't necessarily make things safer, either. That machine might actually contain more credentials for accessing internal company systems.

I didn't want to rely solely on the agent's built-in security mechanisms.

Ways to Isolate AI Agents

There are several ways to isolate an AI agent's execution environment.

  • Separate user account: Simple to set up, but it doesn't fully isolate network access or shared resources.
  • Containers such as Docker: Lightweight and convenient, but they have limitations when working with Windows GUI development tools.
  • Windows Sandbox: Easy to use, but its disposable nature makes it inconvenient for maintaining a long-term development environment.
  • Virtual machine (VM): Provides a separate operating system and file system, with options for network isolation.
  • Separate physical computer: Offers strong separation, but adds hardware and maintenance costs.

None of these approaches guarantees perfect security. The important thing is choosing one that fits your development environment and requirements.

I decided to use a Hyper-V virtual machine.

Why I Chose Hyper-V

The biggest reason I chose Hyper-V was that it lets me run a full Windows GUI development environment with good performance.

I don't want to limit my AI agent to working in a terminal. I also want the option to open projects in Visual Studio, build them, and debug them when necessary. Essentially, I wanted the equivalent of having a second development PC.

Another major factor was startup speed and convenience.

My main development computer is almost always running. If I had a separate physical computer, I'd have to power it on or wake it from sleep whenever I wanted to use it. With Hyper-V, I can simply resume a saved VM. There's no need to boot Windows from scratch, making the process much faster and more convenient.

I also liked Hyper-V's checkpoint feature.

Setting up a development environment from scratch can be tedious. There's Windows, development tools, SDKs, and all sorts of configuration to deal with. With checkpoints, I can restore the VM to a known working state if an agent messes up the environment. That saves me from having to repeat the entire setup process.

Checkpoints aren't a replacement for backups, of course, but they're extremely useful for this purpose.

How I Configured the VM

I installed Windows in the VM and created two separate accounts: an administrator account and a standard user account dedicated to the AI agent.

The administrator account is used only for installing development tools and maintaining the operating system. The AI agent runs under the standard user account, making it harder for the agent to modify system-wide settings.

I also disabled clipboard sharing and file sharing between the host and the VM. These features are convenient, but I saw no reason to provide a potential path for an agent to access passwords copied to the host's clipboard or sensitive files in shared folders.

I configured the VM with essentially the same development environment as my main computer. This means installing Git, SDKs, build tools, and everything else in two places.

Fortunately, my company uses a monorepo, so this wasn't particularly difficult. Multiple projects share a single repository and common build environment, making it relatively straightforward to reproduce the existing setup. Once everything is configured, I can create a checkpoint to make future maintenance easier.

Network Isolation Matters Too

Using a VM doesn't automatically isolate its network access.

Depending on the network configuration, a VM with internet access might also be able to reach the host computer or other devices and services on the company intranet. Separating file systems doesn't help much if the agent can still access internal resources over the network.

That's why I restricted the VM's access to the intranet at the host level.

If the restrictions exist only in the VM's firewall, there's a possibility that the agent could modify those settings. Enforcing restrictions through the host's virtual network and firewall makes them much harder for an agent running inside the VM to change. Of course, the actual protection depends on the network configuration, so the available network paths need to be tested.

I kept internet access enabled. The agent still needs to access Git repositories, download packages, and communicate with AI services. However, internet access also means data can potentially be sent outside the VM, so I keep the credentials stored inside it to a minimum.

The goal is simple: a separate development environment that can access the internet but cannot access my main computer or the company intranet.

Final Thoughts

When using AI agents, I think the important question isn't how much we trust them. It's how much damage they could cause if something goes wrong.

We already follow the principle of least privilege for human developers and separate development environments from production systems. There's no reason to treat AI agents differently. If anything, we should be even more careful, considering how quickly they can execute commands and modify files.

Not everyone needs Hyper-V. A separate user account or Docker container might be sufficient for some workflows.

In my case, I wanted to keep a full Windows GUI development environment while isolating it from my host computer. Add the convenience of quickly resuming a VM and restoring checkpoints, and Hyper-V turned out to be the best fit.

Rather than focusing only on what tasks to give AI agents, I think it's worth considering where they should run and how much access they should have.

For now, I've decided to give my AI coding agent a development PC of its own.
