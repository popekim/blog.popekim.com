A Console Developer's Thoughts on the PS5 Jailbreak

Pope Kim Oct 26, 2026
  • ps5
  • playstation
  • console
  • jailbreak
  • security
  • game dev
  • dev

I've been developing console games for a long time. Compared to PC game development, console development has several advantages. Traditionally, I've considered two of them particularly important.

First, the hardware specifications are fixed. On PC, developers have to account for all sorts of combinations of CPUs, GPUs, memory, and other hardware. On consoles, that isn't necessary. Since every user has essentially the same hardware, performance is much more predictable, and developers can optimize specifically for that hardware. For developers who enjoy squeezing every last bit of performance out of a machine, it's a pretty attractive environment.

Second, security is strong. When you release a game on PC, piracy is something you have to worry about. On consoles, the platform manufacturer takes care of much of that. Instead of spending time implementing copy protection or fighting hackers, developers can concentrate on making better games.

Of course, consoles have never been completely secure. Jailbreaks and piracy have existed for a long time. But they weren't particularly accessible to ordinary users, and some methods required hardware modifications. At least from a developer's perspective, consoles provided a much more comfortable environment than PCs.

Then, recently, I came across some discussion about a PS5 jailbreak on Twitter.

PS5 Relapse? What's that supposed to mean?

I got curious and decided to look into it.

Jailbreaking a PS5 Is This Easy?

Relapse is a jailbreak tool that exploits security vulnerabilities in the PS5 to execute programs that Sony hasn't authorized.

What surprised me was how simple the process looked. On a PS5 running a supported firmware version, you open a particular webpage and launch the jailbreak. After that, you can load and run additional programs.

Wait, jailbreaking a console is this easy now?

What's even more interesting is that the jailbreak isn't permanent. If you fully reboot the console, the changes made in memory disappear, and you have to run the jailbreak again. However, if you leave the console in standby mode, its memory state is preserved, allowing the jailbreak to remain active.

As of October 2026, the publicly available Relapse supports PS5 firmware versions 7.00 through 13.60. The relevant vulnerabilities have been patched in later firmware versions, so this doesn't work on every PS5.

Still, the fact that you can bypass a console's security by clicking a few things on a webpage was pretty shocking.

Didn't We Used to Modify the Hardware?

When I think about console piracy in the past, the first thing that comes to mind is the modchip.

You would open up the console, install an additional chip, and solder wires directly to the appropriate points on the circuit board. The goal was to bypass the console's boot process or security checks so that unauthorized programs or copied games could run.

Of course, software-only jailbreaks existed in the past as well. Not every console required hardware modifications. But many of the earlier methods of circumventing copy protection were closely tied to hardware modifications.

Relapse, however, doesn't require touching the hardware at all.

It's entirely software-based. And it uses the web browser functionality already built into the console.

Simply opening a webpage can become the starting point for bypassing the console's security system.

So I decided to dig a little deeper into how it actually works.

How Can a Web Browser Jailbreak a Console?

Relapse works by chaining together two major stages of exploitation.

The first stage exploits a vulnerability in the web browser. The second exploits a vulnerability in the operating system kernel.

1. Escaping the Web Browser's Security Restrictions

The PS5 includes web browsing functionality based on WebKit. Unlike a typical PC browser, it isn't something users can freely launch and browse with, but the system uses web technologies for things like displaying user guides and other web content.

WebKit is the browser engine used by Safari and several other browsers. It also includes JavaScriptCore, the engine responsible for executing JavaScript.

The problem is that a web browser is a program that executes code obtained from external sources.

When we open a webpage, the browser interprets its HTML and JavaScript and executes the appropriate code. However, that doesn't mean JavaScript can do whatever it wants on the computer. Browsers are designed to execute code within a restricted environment called a sandbox.

Imagine if JavaScript on any random webpage could freely read operating system memory or launch arbitrary programs. Simply browsing the internet would be incredibly dangerous.

But things change when the browser engine itself contains a security vulnerability.

Relapse takes advantage of information disclosure and memory object handling issues in JavaScriptCore. More specifically, it exploits an inconsistency in the state of an internal object pool during object cloning, allowing it to corrupt the internal state of a TypedArray.

A TypedArray is a JavaScript object used to work with binary data. Under normal circumstances, the JavaScript engine controls which memory regions the object can access. However, if a bug in the engine allows the memory information referenced by a TypedArray to be corrupted, it may become possible to access memory outside the normally permitted range.

By exploiting vulnerabilities like these, an attacker can go beyond simply running JavaScript on a webpage and perform operations that wouldn't normally be permitted inside the browser process.

But successfully reaching this point doesn't mean the entire console has been compromised.

After all, the browser is still just another program running on top of the operating system.

2. Now Attack the Kernel

Operating systems prevent ordinary programs from directly accessing critical system resources.

Whether it's a game or a browser, a normal application can only operate within the boundaries permitted by the operating system. The kernel, on the other hand, is the core component responsible for things like process management, memory management, and device control.

If an ordinary application could freely read or modify kernel memory, the operating system's security model could be severely compromised.

That's exactly what Relapse targets next.

Using the execution capabilities obtained through the browser vulnerability, it attacks a separate vulnerability in the operating system kernel.

The vulnerability involved is a Use-After-Free (UAF) issue related to aio_multi_wait.

A UAF is a bug where memory continues to be used after it has already been freed. Imagine an object being deallocated while some other code still holds a reference to it.

In a normal program, this kind of bug might simply cause a crash. But if an attacker can precisely control when the memory is freed, when it gets reused, and what gets written into it, the bug may be exploitable to alter the program's execution flow.

Relapse combines this race condition with address information leaks to obtain the ability to read and write kernel memory.

The important point here is that this isn't merely about calling a function that happens to exist in the kernel.

The key is gaining the ability to read and modify memory managed by the kernel itself.

This can allow an attacker to modify important operating system data structures and change the system state to permit operations that would normally be prohibited.

Of course, reaching this stage doesn't mean every security barrier has disappeared. The PS5 has additional layers of protection beyond the kernel, including a hypervisor. Obtaining kernel-level access and completely defeating every security mechanism in the console are two different things.

Nevertheless, this provides an important foundation for executing programs that ordinary users aren't supposed to run.

3. Running Custom Programs

Once you've reached this point, the next step is relatively easy to understand.

Normally, the PS5 only allows programs authorized and signed by Sony to execute through its official mechanisms. You can't simply create your own executable, copy it to a USB drive, and run it.

But once you've obtained sufficient privileges through security exploits, it becomes possible to build a way around those restrictions.

Relapse includes functionality for launching an ELF loader.

ELF stands for Executable and Linkable Format. It's a binary file format used for executables, libraries, and related files. Developers familiar with Linux or other Unix-like systems have probably encountered it before.

An ELF loader does exactly what its name suggests: it loads an ELF executable into memory and prepares it for execution.

Normally, loading an executable involves placing its code and data into the appropriate memory regions, resolving necessary addresses, and transferring control to the program. Similar operations happen during the normal executable loading process in an operating system.

However, once you've obtained execution privileges through security vulnerabilities, you can also create a way to load ELF programs that the platform would not officially allow.

For Windows developers, DLL injection or API hooking might be useful analogies.

DLL injection is a technique for executing code inside a process that wasn't originally intended to run that code. API hooking intercepts function calls or redirects them to different code, changing how a program behaves.

Of course, Relapse doesn't work in exactly the same way as DLL injection. It first needs to chain browser and kernel vulnerabilities together to obtain the necessary memory access and execution privileges.

But the underlying idea should feel familiar to developers.

You create a way to execute code that the system wouldn't normally allow, and potentially interfere with the behavior of existing programs or the operating system itself.

Once this kind of execution environment is established, various custom programs can be loaded.

After looking into all this, I started seeing that simple jailbreak webpage in a different light.

From the user's perspective, it's just a matter of clicking a few buttons on a webpage. Behind the scenes, however, a fairly sophisticated exploit chain combines a browser memory management bug with a kernel race condition.

The technology required to make the jailbreak possible is anything but simple. It's just that other developers have automated all that complexity, making the end result surprisingly easy for ordinary users.

So What Can You Actually Do with a Jailbroken PS5?

The most immediate change is the ability to run programs that Sony hasn't authorized.

For example, you can run unofficial software commonly referred to as homebrew. This includes tools for examining or modifying internal game data, debugging utilities, file managers, and emulators.

From a game developer's perspective, the ability to run arbitrary debugging tools is interesting in itself.

In an official console development environment, developers use development kits and debugging tools provided by the platform manufacturer. These capabilities are heavily restricted on ordinary retail consoles.

If jailbreaking allows some of those restrictions to be bypassed, it becomes possible to experiment with various tools on consumer hardware.

The problem is that these capabilities aren't necessarily used for good purposes.

They can also be used to bypass security checks, modify game data, run cheat programs, or extract game files. Combined with additional security bypass tools, they may also enable pirated games to run.

Of course, obtaining kernel access doesn't automatically mean every game can be copied and executed. Other protection mechanisms, including game encryption, signature verification, and the hypervisor, still matter.

But it certainly provides an important tool for bypassing parts of the console's security system.

One of the reasons I enjoyed console development was that I didn't have to worry nearly as much about this kind of thing.

On PC, it's relatively easy to examine or modify executable files. Developers may have to consider what protection mechanisms to implement and how to deal with piracy or cheating.

On consoles, however, the platform manufacturer provides a strong security system. Developers can concentrate on building the game on top of that foundation.

Of course, this doesn't mean console game developers can completely ignore cheating or security. Server-side validation and anti-cheat measures are particularly important in online games. But at least developers don't have to take responsibility for building the platform's copy protection system from scratch.

I really liked that part of console development.

How Did Consoles End Up Like This?

This is the part that got me thinking even more than the technical details of Relapse.

I feel that the fundamental direction of game consoles has changed quite a bit over the years.

Consoles Used to Be Seriously Powerful Gaming Machines

Think back to the days when the PS3 and Xbox 360 were released.

Back then, a console wasn't simply a cheap gaming PC. It was a machine that could compete with high-end PCs of its time while offering that level of hardware at a relatively affordable price.

The Xbox 360, released in 2005, used an IBM PowerPC-based CPU with three cores. Its GPU, ATI's Xenos, adopted a unified shader architecture that hadn't yet become common in PC graphics cards.

Instead of dividing hardware resources into separate, fixed vertex shader and pixel shader units, the unified shader architecture allowed those resources to be shared. This eventually became the mainstream approach in PC graphics hardware as well.

The Xbox 360 launched in the United States at $299 or $399, depending on the model. That was a remarkably affordable way to get a system equipped with such powerful graphics hardware at the time.

The PS3, released the following year, took things even further.

Its Cell processor was designed in a radically different direction from conventional PC processors. It combined a PowerPC-based PPE with multiple SPEs to process large amounts of data in parallel.

It certainly wasn't easy hardware to develop for. In fact, it could be a real headache when you first started working with it.

But if you knew how to use it properly, you could extract tremendous computational performance for its time. There was a very clear reason for game developers to understand the hardware and write code specifically for it.

The PS3 and Xbox 360 had very different architectures, but they shared something important.

They aggressively introduced cutting-edge technologies into game consoles and encouraged developers to squeeze as much performance as possible out of the hardware.

Development could be difficult, but there was a real payoff for understanding and using the hardware well.

Things Changed with the PS4

With the PS4 and Xbox One generation, however, things started moving in a different direction.

Both consoles adopted AMD Jaguar CPUs based on x86-64, along with Radeon-based GPUs.

Using architectures similar to those found in PCs was certainly good news for developers. There was less need to learn completely different CPU architectures or write large amounts of console-specific code.

But there was another change in terms of hardware performance.

By the time the PS4 launched in 2013, you could already buy PCs equipped with more powerful CPUs and GPUs. Rather than introducing cutting-edge hardware that outperformed high-end PCs, the PS4 offered a balanced design that considered price, power consumption, and manufacturing costs.

Of course, even earlier consoles weren't necessarily superior to high-end PCs in every component or every workload. The PS3 wasn't faster than contemporary high-performance PCs at everything either.

Nevertheless, I felt that the overall design philosophy had clearly changed.

In the past, manufacturers had designed unusual and aggressive hardware specifically for gaming. Now they were moving toward combining widely available, general-purpose technologies to build reasonably priced consoles.

There are plenty of advantages to this approach.

Development becomes easier, and porting games between PCs and consoles becomes more straightforward. Hardware development costs and risks are also reduced. And the actual gaming experience consumers get at a given price doesn't necessarily become worse.

From the console manufacturers' perspective, it's an entirely reasonable decision.

But for developers who enjoy pushing hardware to its limits, it inevitably feels different from the old days.

From Dedicated Gaming Machines to Living Room Entertainment Devices

Another noticeable change is the role consoles are expected to play.

Of course, older consoles weren't exclusively for games either. The PS2 served as a DVD player, and the PS3 became popular as a Blu-ray player. The Xbox 360 also offered online services and various media features.

So it's not as though media functionality suddenly appeared with the PS4.

However, as console generations progressed, the effort to position consoles as comprehensive living room entertainment devices rather than just gaming machines became more apparent.

Video streaming, music, web content, and various online services became increasingly important alongside games.

For consumers, that's a good thing. If you're going to have a device in your living room anyway, it's convenient to use it for games, movies, and other services.

But from a security perspective, things look a little different.

As more features are added, more software needs to be included in the system. There's more code processing data obtained from external sources, and more libraries and services that need to be maintained.

In security terminology, this is referred to as the attack surface.

It represents the potential entry points where an attacker might discover and exploit vulnerabilities.

Web browsers are a perfect example.

A web browser is an extremely complex piece of software. It processes many different types of external data, including HTML, CSS, JavaScript, images, and video. It also uses sophisticated techniques such as JIT compilation and complex memory management to improve performance.

With software this complicated, bugs are practically inevitable.

Of course, simply having a web browser doesn't mean a console can necessarily be jailbroken. Relapse didn't bypass the PS5's security through a browser vulnerability alone. It also needed to exploit a separate kernel vulnerability.

And using general-purpose hardware doesn't inherently make a system less secure either.

However, as you continue adding general-purpose software and functionality to a dedicated gaming system, it's difficult to avoid increasing the number of places an attacker might investigate.

The fact that Relapse uses the web browser as its entry point felt rather symbolic to me.

We've reached a point where a machine built to run games can be jailbroken through a webpage.

I Miss the Days When We Could Just Focus on Making Games

Of course, I wouldn't conclude that the PS5 has terrible security based on this incident alone.

Relapse doesn't rely on bugs that just anyone could easily discover. It's the result of finding and chaining together complicated browser memory vulnerabilities and kernel vulnerabilities.

And the relevant vulnerabilities have been patched in newer firmware versions. The exploit only works on supported older firmware, and jailbreaking a console doesn't mean you can suddenly run every game you want.

It wouldn't be fair to say that Sony hasn't taken security seriously.

But what struck me as a developer was something a little different.

One of the great things about console development in the past was that you could push fixed hardware to its limits while leaving much of the platform security to the manufacturer. That allowed you to focus on making the game itself.

Of course, those advantages still exist on modern consoles. The PS5 still has a far more consistent hardware configuration than PCs, and its security architecture is very different from that of a typical open PC platform.

But the days when consoles introduced radically different, cutting-edge hardware are largely behind us. Their hardware architectures have become more similar to general-purpose computers, while their operating systems and software have grown increasingly complex.

That isn't necessarily a bad thing. In fact, considering development and manufacturing costs, it's probably a sensible direction.

Still, I personally find it a little disappointing.

Back then, there was something exciting about accomplishing things on console hardware that weren't easy to achieve on PCs. How well you understood and utilized the hardware could make an enormous difference in performance.

At the same time, you could rely heavily on the platform manufacturer's security system for things like copy protection.

From a developer's perspective, that was a pretty nice combination.

I haven't completely left console game development behind. But compared to the past, I feel that much of what made consoles uniquely interesting has changed.

And hearing that a PS5 can now be jailbroken with a few clicks on a webpage really brought that change home.

Well, I suppose technology in the game industry was always going to keep changing.

Appendix: Can You Run PS3 Games on a Jailbroken PS5?

While looking into Relapse, I came across someone saying that jailbreaking a PS5 would also let you run PS3 games.

That got me thinking about something else.

If you wanted to emulate older PlayStation games on a PS5, which would be the most difficult: PS2, PS3, or PS4?

You might assume that the older the console, the easier it would be to emulate. But that isn't necessarily true.

When it comes to emulation, the original hardware's performance matters, but so does how different its architecture is from the host system.

PS2: Modern Hardware Can Brute-Force Its Way Through

The PS2 was released in 2000.

It used a distinctive processor called the Emotion Engine and a graphics processor called the Graphics Synthesizer.

The CPU was based on the MIPS architecture and used multiple vector processing units to perform the calculations needed by games.

It was impressive hardware at the time, but its absolute processing power is extremely low by modern standards.

Of course, accurately reproducing the PS2's hardware behavior still isn't an easy task. Its unusual memory architecture, vector processing units, and graphics pipeline all need to be considered.

But modern CPUs and GPUs provide vastly more computational power than the PS2.

That means they have enough performance headroom to absorb the substantial overhead introduced by emulation.

In fact, we've been running PS2 games on PCs through emulators like PCSX2 for many years.

More recently, projects like PS5SX2 have appeared, allowing PS2 emulation on jailbroken PS5 consoles.

The PS2 has a distinctive hardware architecture, but modern hardware has become powerful enough to overcome much of that difference.

PS4: The Architecture Is Almost the Same

The PS4 is a different story.

Both the PS4 and PS5 use AMD CPUs based on x86-64. Their GPUs also belong to AMD's Radeon family.

This means there's no need to translate CPU instructions from one completely different architecture to another.

Of course, that doesn't mean running PS4 games on a PS5 is as simple as copying an executable file.

You still need to handle the operating system APIs, memory management behavior, GPU commands, file system, and system services that the game expects.

The GPUs in the PS4 and PS5 aren't identical either.

But sharing the same CPU instruction set architecture is already a significant advantage. You don't need to interpret every CPU instruction in software or translate it into instructions for a completely different processor architecture.

After all, the PS5 officially provides backward compatibility with most PS4 games. The similarity between the two systems' hardware architectures plays an important role in making this possible.

Implementing an unofficial execution environment is a separate challenge, but having similar CPU architectures is certainly a major advantage.

PS3: Now That's a Headache

The PS3 is an entirely different story.

Its Cell processor combined a PowerPC-based PPE with multiple SPEs.

The PPE handled general program execution and task management, while the SPEs were designed to process large amounts of data in parallel.

The SPU inside each SPE, in particular, operated very differently from a conventional CPU core.

Each SPU had its own local memory, and data transfers worked differently from those in a typical shared-memory CPU architecture. Programs often had to explicitly move data around before performing calculations.

Some PS3 games made extensive use of this architecture.

The problem is that reproducing this behavior on a modern x86-64 CPU isn't easy.

It isn't simply a matter of translating one instruction into another. You also need to reproduce memory transfers, parallel execution, synchronization, timing, and various other behaviors.

On top of that, the PS3's SPUs were remarkably powerful at certain kinds of vector computations.

Of course, modern CPUs are vastly more capable than the PS3's processor overall. But in an emulator, you aren't executing the original hardware's instructions directly. You're reproducing their behavior on hardware with a different architecture.

That process can introduce substantial performance overhead.

In fact, there were experiments in 2026 involving running Linux on a PS5 and using the RPCS3 emulator to execute PS3 games.

The results were interesting.

Games that didn't make heavy use of the SPUs ran relatively well. But in games that relied heavily on SPU processing, the PS5's CPU sometimes struggled enough that the games ran more slowly than they did on the original PS3.

Just because the PS5 is a much newer console doesn't mean it can effortlessly emulate every aspect of the PS3.

Ultimately, the difficulty of emulation isn't determined solely by how old the original console is or how much raw processing power it had.

What really matters is how efficiently you can bridge the gap between two different hardware architectures.

Come to think of it, this also relates to what made console development so interesting in the past.

Unusual hardware like the PS3 made developers' lives difficult, but there was also a lot of satisfaction in understanding that hardware and learning how to use it properly.

And now, all these years later, that same unusual architecture is giving emulator developers headaches all over again.
