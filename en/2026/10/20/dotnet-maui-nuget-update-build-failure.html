What to Do When a .NET MAUI Update Breaks Your Build on Windows + Visual Studio

Pope Kim Oct 20, 2026
  • dotnet
  • maui
  • nuget
  • visual studio
  • vcs
  • dev

When developing a .NET MAUI project with Visual Studio on Windows, you'll occasionally see a long list of available updates in the NuGet Package Manager. You update the packages as usual, and suddenly your build breaks. Sound familiar? If this happens right after updating MAUI-related packages such as Microsoft.Maui.Controls, this article is for you.

Unlike ordinary NuGet packages, .NET MAUI requires a little more attention when it comes to updates.

.NET MAUI Doesn't Run on NuGet Packages Alone

.NET MAUI depends on two main components:

  1. NuGet packages: Libraries referenced by your project, such as Microsoft.Maui.Controls.
  2. .NET workloads: SDKs and tools required to build for platforms such as Android, iOS, and Windows.

The problem is that these components are updated separately. Updating a NuGet package doesn't automatically update the workloads required by that version.

For example, suppose you update your project to reference a newer version of Microsoft.Maui.Controls, but your development machine still has an older workload installed. This can lead to compatibility issues, resulting in build errors or warnings about mismatched package versions.

Of course, this doesn't mean the NuGet package and workload version numbers must match exactly. What matters is that you're using compatible versions.

How Do You Fix This on Windows + Visual Studio?

If the problem started immediately after a NuGet update, first roll back the affected packages to their previous versions. This makes it easier to confirm whether the update caused the problem.

Next, launch Visual Studio Installer and update Visual Studio and the MAUI development components.

When using Visual Studio on Windows, .NET MAUI workloads are generally managed through Visual Studio Installer. It's better to use Visual Studio Installer rather than updating the workloads separately through command-line tools.

There's one thing to watch out for. If you search online for instructions on updating MAUI, you'll probably come across this command:

dotnet workload update

However, don't blindly run this command in a Windows development environment managed by Visual Studio Installer.

Mixing workloads installed through Visual Studio Installer with those installed through the CLI can create confusion around installation state and version management. If Visual Studio manages your development environment, it's safer to use the same mechanism for updates.

So, follow these steps:

  1. Roll back the MAUI NuGet packages that caused the problem to their previous versions.
  2. Update Visual Studio and the MAUI development components through Visual Studio Installer.
  3. Update the necessary MAUI NuGet packages again, making sure the versions are compatible.
  4. Build the project and verify that everything works.

Of course, updating Visual Studio to the latest version doesn't guarantee compatibility with every latest MAUI NuGet package. You still need to check which versions are supported by your .NET SDK and Visual Studio installation.

Do You Really Need to Manage Workload Versions Separately?

.NET MAUI also allows you to explicitly manage SDK and workload versions using global.json and Workload Sets. This can be necessary, especially in macOS or CLI-based development environments.

But if every developer uses Windows + Visual Studio and your team has standardized its development environment, that's a different story.

If Visual Studio Installer already manages your workloads, why introduce separate CLI commands and another version management process?

Having two different ways to manage the same development environment may simply create more opportunities for things to go wrong.

Conclusion

.NET MAUI isn't just another NuGet library. The packages referenced by your project must also be compatible with the workloads installed in your development environment.

So, if your build breaks right after updating MAUI-related NuGet packages, don't start blindly updating other packages. Roll back the changes first and confirm what caused the problem.

And if your team has standardized on Windows + Visual Studio, update the MAUI development environment through Visual Studio Installer before updating the NuGet packages.

There's no need to introduce a complicated workload version management system when your development environment is already standardized. Standardizing the environment itself takes care of much of the version management problem.

The goal of version management isn't to maintain complicated configurations. It's to ensure that you can build your project reliably, anytime and anywhere.
