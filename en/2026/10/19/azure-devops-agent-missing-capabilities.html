Azure DevOps Agent Capabilities Disappearing? Windows Compression Might Be the Culprit

Pope Kim Oct 19, 2026
  • dev
  • windows
  • dotnet
  • debugging
  • build

At my company, we run a self-hosted build farm consisting of multiple Windows machines, each running an Azure DevOps build agent. Everything had been working fine until around April of this year, when we started encountering a rather strange problem.

After rebooting a build machine, its Azure DevOps agent would sometimes fail to register its System Capabilities properly.

Capabilities tell Azure DevOps which development tools and environments are available on an agent. For example, they include information about installed tools such as MSBuild and Visual Studio, along with their installation paths. Azure DevOps uses this information to assign build jobs to suitable machines. If these capabilities disappear, an agent may no longer qualify for certain build jobs, even though all the required development tools are still installed and working perfectly fine.

Completely Inconsistent Symptoms

Initially, I assumed something had gone wrong during agent initialization. But the behavior was bizarre.

  • Some machines would return to normal after a reboot.
  • Others would remain broken no matter how many times we rebooted them.
  • Even on the same machine, the problem would appear on some days but not others.
  • Restarting the agent service didn't fix anything.

Our build farm uses separate accounts for administration and for running the actual build agents. Naturally, I suspected some kind of permission issue or a race condition during initialization.

But while investigating, I discovered something even stranger.

Simply opening Command Prompt (cmd.exe) as Administrator could make the problem go away.

I didn't even have to execute a command. Just opening an elevated Command Prompt was sometimes enough for the capabilities to register properly afterward.

At that point, I started to suspect this wasn't merely an Azure DevOps configuration issue.

Clues in the Diagnostic Logs

Azure DevOps agents write diagnostic logs to the _diag directory under their installation folder. If your agent isn't registering its capabilities properly, that's a good place to start looking.

In our case, exceptions related to the .NET Framework provided some clues. In particular, the following keywords are worth searching for:

  • MarvinHash
  • ServicePointManager
  • System.Configuration.ConfigurationErrorsException

Seeing these errors doesn't necessarily mean you're experiencing the same problem. However, if you encounter related exceptions during capability detection, it's worth checking the Windows file compression state described below.

I'll spare you the details of all the troubleshooting. In the end, the solution turned out to be somewhere rather unexpected.

The Culprit: Windows WOF Compression

The problem involved this file:

C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config\machine.config

machine.config is a global configuration file used by the .NET Framework. It turned out that this file was compressed using WOF (Windows Overlay Filter).

WOF allows Windows to store files in a compressed format and decompress them transparently when needed. It's also used by Windows Compact OS and works differently from regular NTFS compression. Its primary purpose is to save disk space, particularly for executables and files that rarely change.

There's nothing inherently wrong with this compression. It's a normal Windows feature.

The problem appears to be that something went wrong when the .NET Framework tried to access this file in our environment. I haven't determined exactly where the failure occurred internally, or why simply opening an elevated Command Prompt could change the behavior.

What I did confirm, however, is that the problem disappeared after decompressing the file.

How to Check and Fix It

First, open Command Prompt (cmd.exe) as Administrator.

Check the compression status of both the 32-bit and 64-bit .NET Framework machine.config files:

compact "C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config\machine.config"
compact "C:\Windows\Microsoft.NET\Framework64\v4.0.30319\Config\machine.config"

If either file is compressed, decompress it using the following commands. In our case, we ran both commands regardless of the files' existing compression states.

compact /U /F /EXE "C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config\machine.config"
compact /U /F /EXE "C:\Windows\Microsoft.NET\Framework64\v4.0.30319\Config\machine.config"

Here's what each option does:

  • /U: Decompresses files.
  • /F: Forces the compression or decompression operation.
  • /EXE: Handles WOF-compressed files rather than just regular NTFS compression.

The important part here is the /EXE option. Without it, the command only handles regular NTFS compression, potentially leaving WOF-compressed files untouched.

Once decompression is complete, run the compact commands again to verify the status of both files. Then reboot the machine and check whether the agent's System Capabilities are properly registered in Azure DevOps.

This resolved the issue for us.

Applying the Fix to the Rest of the Build Farm

After confirming that decompression fixed the affected machines, we applied the same change to the rest of our build farm.

Not every machine had experienced the problem. Some had been running perfectly fine all along, but there was no guarantee they wouldn't encounter it in the future.

Besides, machine.config is a tiny configuration file. Decompressing it has a negligible impact on disk space. We saw no compelling reason to keep it compressed, so we decompressed both the 32-bit and 64-bit versions on every build machine.

Final Thoughts

We had been dealing with this intermittent issue for months, and in the end, the fix was as simple as decompressing a small configuration file.

I still don't know exactly why WOF compression caused this behavior. It could be a problem in a particular Windows or .NET Framework code path, or perhaps an interaction with some other environmental factor. Pinpointing the actual internal failure would require further investigation.

What I can say is that decompressing the file resolved the problem on machines where we had been experiencing it.

If your Azure DevOps agent suddenly loses its System Capabilities after a reboot, check the compression status of machine.config before spending hours messing around with the agent configuration.

You might be surprised at how simple the fix turns out to be.
